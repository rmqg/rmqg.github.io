前幾天在群組裡看到一張「三十日推歌大挑戰」的問卷，忽然覺得這種玩法不應該只停留在一張圖片上：如果每個人都能真正選擇歌曲、聽別人推薦、按讚評論，再把結果留存下來，它會更像一個持續發生的小型音樂交換會。

於是有了 **推歌挑戰**。

## 不是固定的三十題問卷

最初那張圖只是一份範例，不是所謂的「經典題庫」，更不是網站的預設內容。新挑戰的題庫預設留空，發起者可以自己寫任意數量的問題，也可以載入三十題範例，或者直接上傳一張已有問卷圖片，讓視覺模型辨識成可編輯的題目列表。

題目可以一次性全部開放，也可以每天開放一道。逐日開放統一按照北京時間計算，首頁只展示當前已經開放、但自己還沒有回答的挑戰；已經答完的內容不會繼續佔著待辦區域。

## 用歌回答，也圍繞歌交流

每道題可以選擇一首或多首歌曲，並補充一段感想。目前支援嗶哩嗶哩影片和網易雲單曲連結，其他參與者可以直接播放來源頁面、按讚和評論。

網站還保留了原問卷裡很有意思的「印象曲」玩法：給群友一個關鍵詞，對方再為這個詞選擇一首歌。相關互動會透過站內通知送達，並準確跳轉到對應題目和答案。

公開挑戰可以在廣場被發現；Token 挑戰則使用六位數字邀請憑證。分享海報會列出最多三列、三十道題，並帶有二維碼；Token 挑戰的二維碼可以直接攜帶邀請資訊。

## 「智慧搜尋」如何尋找本家

只輸入歌名時，伺服端會讀取 B 站前三頁、最多五十項真實搜尋結果，再把標題、投稿者、簡介和發布日期等證據交給模型篩選。模型不會輸出容易抄錯的 BV 號，只返回候選序號，真實連結由伺服端回填。

篩選結果包含原創本家、翻唱、官方重製、二創等結構化分類。播放量可以作為弱輔助證據，但不會壓過標題、來源與發布時間。成功結果會按正規化歌名永久快取，同一首歌之後不再重複花費模型 token。

## 實作與維運

專案使用 Next.js 16、React 19、Better Auth、Drizzle ORM 和 PostgreSQL 17，部署在 Docker Compose 中。圖片題庫經 OpenRouter 視覺模型轉錄，歌名篩選使用 DeepSeek；平台邏輯都隔離在適配器之後。

生產環境包含健康檢查、資料庫備份、平台 Cookie 登入狀態監控和 Bark 斷線提醒。敏感設定只放在伺服器 secret 中，不進入前端、記錄檔或 Git 儲存庫。

專案以 **GPL-3.0-only** 開源。現在的介面和規則當然還會繼續變化，但至少下一次群組裡再出現一張推歌問卷時，我們可以真正一起玩起來了。

## 開源發布補記

**GitHub：** [rmqg/playlist-challenge](https://github.com/rmqg/playlist-challenge)

`playlist-challenge` 現已作為完整的公開儲存庫發布在 [GitHub](https://github.com/rmqg/playlist-challenge)。首頁先寫給想和朋友一起推歌的人：怎麼出題、怎麼答、怎樣交換感受；後半部分也保留了自託管、部署與貢獻入口。

儲存庫補齊了 GPL 版權與第三方通知、脫敏的部署範本、貢獻與安全政策，以及自動執行型別檢查、靜態檢查、測試和生產建置的 CI。平台 Cookie、模型金鑰、Bark 設定和執行資料都不會進入公開儲存庫。

圖片題庫在境外生產伺服器仍預設使用 OpenRouter：實際連線矽基流動服務的效果不佳。對於在中國大陸部署、並願意自行從目標伺服器驗證延遲與穩定性的開發者，儲存庫另附了[矽基流動 SDK 設定參考](https://github.com/rmqg/playlist-challenge/blob/main/docs/SILICONFLOW.md)。
